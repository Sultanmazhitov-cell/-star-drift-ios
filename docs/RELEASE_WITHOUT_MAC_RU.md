# Сборка и выпуск без своего Mac

Исходники можно хранить в GitHub и собирать на облачном Mac в GitHub Actions. Личный Mac для этого пути не нужен. Для TestFlight и App Store всё равно потребуются участие владельца в Apple Developer Program, подпись приложения и запись в App Store Connect.

## 1. Проверить сборку в браузере

1. Создать репозиторий GitHub. Если исходники должны оставаться закрытыми, выбрать **Private**.
2. Загрузить содержимое папки проекта в корень репозитория: рядом должны лежать `StarDrift.xcodeproj`, `StarDrift/` и `.github/`.
3. Убедиться, что загрузилась скрытая папка `.github/workflows`.
4. Открыть вкладку **Actions**, разрешить запуск workflow при необходимости, выбрать **Build iOS simulator app** и нажать **Run workflow**. При изменениях в ветке `main` сборка запускается автоматически.
5. Дождаться результата. Внизу страницы запуска появятся **StarDrift-Simulator** (сборка) и **StarDrift-UI-Results** (отчёт тестов, снимки экранов и журнал). Сборка может сохраниться даже при последующей ошибке теста — проверяйте результат всего запуска.

После компиляции workflow выбирает доступный симулятор iPhone и запускает автоматическую проверку: старт, пауза, продолжение, открытие настроек и переключение звука. В отчёте сохраняются снимки начального экрана, игры, паузы и настроек. [Текущий проект уже прошёл эту проверку в облаке](https://github.com/Sultanmazhitov-cell/-star-drift-ios/actions/runs/40383237327); снимки находятся в `docs/screenshots`.

Workflow собирает приложение для симулятора без подписи. ZIP с `.app` **нельзя установить на обычный iPhone или загрузить в App Store**. Его задача — проверить проект компилятором Xcode и передать сборку тому, у кого есть iOS Simulator. Проверка не заменяет игру на настоящем устройстве.

Стоимость и доступные минуты облачного Mac зависят от тарифа GitHub. До первого запуска проверить лимиты своего аккаунта.

## 2. Один раз подготовить Apple Developer

Владелец вступает в Apple Developer Program, принимает соглашения Apple и на странице **Certificates, Identifiers & Profiles** регистрирует уникальный App ID. Для этой игры дополнительные capabilities не нужны. Затем создаёт приложение с тем же Bundle ID в App Store Connect. Значение `com.example.StarDrift` является образцом: для выпуска нужен собственный идентификатор.

Для ручной подписи нужны сертификат **Apple Distribution** вместе с его приватным ключом и профиль **App Store Connect** для выбранного App ID. Если они уже есть, повторно создавать их не нужно. Профиль и сертификат должны принадлежать одной Apple Developer Team.

### Получить сертификат без Mac

Эти команды выполняются один раз на доверенной машине с OpenSSL — например, в Linux или Windows с установленным OpenSSL. Работать в отдельной приватной папке **вне репозитория**. Не использовать случайные сайты для генерации ключей.

```bash
openssl req -new -newkey rsa:2048 -keyout distribution.key -out distribution.csr
```

OpenSSL запросит пароль для приватного ключа и данные владельца. Сохранить пароль. В браузере на сайте Apple Developer создать сертификат **Apple Distribution**, загрузить только файл `distribution.csr` и скачать выданный `distribution.cer`. Приватный файл `distribution.key` на сайт Apple не загружать.

В той же приватной папке преобразовать сертификат и объединить его с ключом:

```bash
openssl x509 -inform DER -in distribution.cer -out distribution.pem
openssl pkcs12 -export -inkey distribution.key -in distribution.pem -out distribution.p12
```

При экспорте задать отдельный непустой пароль `.p12` — он понадобится workflow. На странице Apple Developer создать профиль распространения **App Store Connect**, выбрать App ID и этот сертификат, затем скачать профиль. В командах ниже скачанный файл назван `StarDrift.mobileprovision`.

```bash
openssl base64 -A -in distribution.p12 -out distribution.p12.b64
openssl base64 -A -in StarDrift.mobileprovision -out StarDrift.mobileprovision.b64
```

Файлы `.b64` тоже являются секретами. Их содержимое переносится в GitHub Secrets; в репозиторий они не попадают. Надёжно сохранить исходный приватный ключ и сертификат, после настройки удалить временные копии из рабочей папки.

### Получить ключ загрузки App Store Connect

В App Store Connect открыть **Users and Access → Integrations → App Store Connect API**. При необходимости Account Holder сначала запрашивает доступ к API. Создать командный API key с правами, достаточными для загрузки приложения; для этого процесса обычно подходит роль **App Manager**. Сохранить **Key ID**, **Issuer ID** и один раз скачиваемый `.p8`. Это отдельный ключ, он не заменяет сертификат подписи.

## 3. Загрузить сборку в TestFlight из браузера

В репозитории GitHub открыть **Settings → Secrets and variables → Actions → New repository secret** и добавить:

| Имя секрета | Значение |
| --- | --- |
| `IOS_DISTRIBUTION_P12_BASE64` | Содержимое `distribution.p12.b64`. |
| `IOS_DISTRIBUTION_P12_PASSWORD` | Пароль, заданный при экспорте `.p12`. |
| `IOS_APP_STORE_PROFILE_BASE64` | Содержимое `StarDrift.mobileprovision.b64`. |
| `APPLE_TEAM_ID` | Team ID из Apple Developer Membership. |
| `APP_BUNDLE_ID` | Зарегистрированный Bundle ID, совпадающий с записью в App Store Connect. |
| `ASC_KEY_ID` | Key ID ключа App Store Connect API. |
| `ASC_ISSUER_ID` | Issuer ID этого командного ключа. |
| `ASC_PRIVATE_KEY` | Полный текст `.p8`, включая строки `BEGIN PRIVATE KEY` и `END PRIVATE KEY`. |

Сертификаты, ключи и пароли не присылать в чат. Ограничить доступ к репозиторию и его Actions. Запускать выпуск только из проверенной версии исходников.

Открыть **Actions → Upload to TestFlight → Run workflow** и вручную выбрать нужную ветку. В отличие от обычной проверки сборки, этот workflow не запускается при push и pull request. Он:

- проверяет наличие секретов, срок профиля и соответствие Team ID/Bundle ID;
- устанавливает сертификат во временную keychain;
- собирает архив для настоящего iOS-устройства с ручной подписью;
- экспортирует пакет `app-store-connect` и загружает его в App Store Connect;
- удаляет временные ключи, профиль, keychain и файлы сборки, в том числе после ошибки.

При архивировании Bundle ID и Team ID передаются из секретов, номер сборки — из номера запуска GitHub Actions. Версия приложения берётся из проекта. Для первой версии это подходит; если в App Store Connect уже есть сборки с большим номером, нужно согласовать нумерацию перед запуском.

Зелёный результат загрузки ещё не означает готовность к тестированию: дождаться обработки сборки в App Store Connect, заполнить запрошенные сведения и включить её в TestFlight. Затем проверить на iPhone управление, паузу при сворачивании, звук, тактильный отклик, рекорд, разные размеры экрана и работу без интернета. Для внешних тестировщиков Apple может потребовать отдельную проверку TestFlight.

Workflow выбирает последнюю стабильную версию Xcode, доступную в образе `macos-15`; её версия выводится в журнале. Перед выпуском убедиться, что SDK соответствует текущим требованиям Apple. Подготовленный workflow не исполнялся в этой Linux-среде, поэтому работу подписи и загрузки подтверждает только реальный запуск с действующими данными владельца. Подписанный `.ipa` в комплекте не поставляется.

## 4. Отправить на проверку

Заполнить карточку приложения по `APP_STORE_RU.md`, разместить публичные страницы поддержки и конфиденциальности, загрузить снимки экрана из iOS-сборки и проверить анкету App Privacy. После тестирования выбрать нужную подписанную сборку и отправить её на App Review из аккаунта владельца.

`Upload to TestFlight` не отправляет приложение на App Review и не включает публикацию. В этом комплекте нет действующих сертификатов, подписанного `.ipa` и готовой записи App Store Connect. На Linux проверяется состав проекта; успешную компиляцию подтверждает только запуск Xcode на macOS. Одобрение и публикация зависят от проверки Apple.
